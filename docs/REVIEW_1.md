### 2.2 モクリはなぜ落ちたか

参照は `_private/e2e-ds/refs/` にある DS 世代の市販スプライト 4 点（人物 3、生き物 1）。計測だけに使った。数値は 1 フレーム目の不透明ピクセルが対象。

**要因 1: 楕円の積み木でできている。**
- 適用された Op の内訳は、`ellipse` 26、`polygon` 4、`stroke` 7、`outline` 6。手で置いた行データ（`draw_rows`）は 10 回、合計 244 マス（透明の `.` を含む）。不透明 3269 px のうち、手で置いたのは 7.5% 以下である。

**要因 2: 目の設計。**

| | モクリ | 参照の生き物 |
|---|---|---|
| 目の大きさ | 手前 8×8、奥 5×7 | 12×11 |

| ×1 での見え方 | 黒い点が 2 つ | 輪として読める |

- 顔は正面、胴は横向きで、斜め向きの遠近が成り立っていない。両目はほぼ同じ高さにあり、間隔（9 px）が目の幅より広い。

**要因 3: 陰影が形を説明していない。**
- 影は、頭と胴の右下の縁に沿った厚さ 3〜5 px の三日月。ハイライトは左上の 11×6 の楕円。球を描くときの塗り方である。

**要因 4: 80×80 に見合う情報がない。**

**要因 6: 工程。**
- 設計原画がなく、描きながら設計している。

### 2.3 なぜ大きいと落ちるのか

- 16〜32 px では、1 px がそのまま意味の単位になる（目は 2 px）。図形と行データで足りる。
- 80 px では部品の設計が要る。ところが、道具がいちばん安くしている操作は楕円である。形 × 色で守りながら塗る手段がなく、影は塗り重ねでしか作れない（DS 報告 §6-3）。作り手は安い操作に流れる。

### 3.1 プラットフォーム機構（申し送り 2・3、DM 知見 1・4。H-01〜H-06）

#### 3.1.1 名前

申し送りの「サイズクラス／機種仕様プロファイル」を、仕様とデータでは **プラットフォーム（`platform`）** と呼ぶ。次の 3 つと名前がぶつかるためである。

- MCP の公開範囲 `--profile standard|minimal`（§10.1.2）
- `canvas.color_profile`（§5.3.1）
- `import_image` の配置先を表す引数 `target`

#### 3.1.2 考え方

1. **粒度が第一級。機種は、その具体例。** プラットフォームは「表示系（system）」と「アセットの役割と大きさ（asset）」の組である。制約を何も持たない表示系 `free` があるので、任意の粒度を機種と無関係に宣言できる。ゲームボーイは、制約をたくさん持つ表示系の 1 例にすぎない。
2. **宣言データであり、コードではない。** JSON で書く。内蔵、利用者の設定ディレクトリ、ファイル指定、プラグインのどれからでも足せる。全フィールドが省略できる。
3. **プロジェクトにはスナップショットを埋める。** 名前の参照ではなく、解決済みの全体を `project.json` に持つ。同じ `project.json` と同じツール版から同じ検証結果が出る（原則 4）。プリセットを後で直しても、既存のプロジェクトは変わらない。
4. **制約と作法を分ける。**
   - 制約（色の深さ、パレットの構造、タイル、大きさ）は機械で判定でき、エラーや警告になる。
   - 作法（陰影の段数、目の比率、占有率）は測った目安で、**情報の水準を超えない。** 表現を縛らない、という思想を守る。
5. **整数だけ。** 比は千分率、時間は有理数（分子と分母）で持つ。

|---|---|---|---|
| `class` | 文字列 | `sprite-16` `sprite-80` `tileset-8` `background` `ui-icon-16` など | — |
| `role` | 文字列 | `sprite` / `tileset` / `background` / `ui` / `portrait` / `effect` | — |

| `colors.opaque_max` | 整数 / `null` | 1 フレームの不透明色の上限 | Q-PAL-05（書き写し） |
| `animation.tick` | `{num, den}` / `null` | 時間の単位（秒）。60 分の 1 秒なら `{1, 60}`、24 fps なら `{1, 24}` | Q-PLT-07 |
| `animation.tags` / `tags_optional` | 文字列の配列 | あるべきタグと、あってもよいタグ（例: `idle` `attack` `hurt` `death` `skill` `power`） | Q-PLT-08 |
| `animation.frames_max` | 整数 / `null` | フレーム数の上限 | Q-PLT-08 |

**`defaults`**: `grid`（`canvas.grid` の升目）、`palette`（`new` の既定パレット）、`preview.scale` と `preview.backgrounds`（レビューシートが使う背景色の列）、`export.scale`、`export.review_scale`、`export.sheet`、`pipeline.preset` と `pipeline.overrides`。呼び出しが引数を明示したら、常に引数が勝つ。既定値がプラットフォームから来たことは、結果の封筒の `defaults_from_platform`（使ったキーの一覧）に入れる。

**表示時間と `tick`。** 表示時間は整数ミリ秒のまま持つ（§5.4）。24 fps は 1 コマ 41.67 ms で、整数にならない。次の規則で決定的に割り振る。

- タグの中で先頭から数えて `k` 番目（0 始まり）までの累積コマ数を `T(k)` とする。`T(k)` コマ目の終わりの時刻は `floor(T(k) × 1000 × num / den)` ミリ秒。各フレームの表示時間は、その差である。
- 24 fps で 1 コマずつなら 41、42、42、41、42、42…となる。
- この割り振りを行う Op `set_frame_ticks`（フレーム指定と、各フレームのコマ数）を足す。Q-PLT-07 は、表示時間がこの規則から 1 ms を超えてずれたフレームを指摘する。

#### 3.1.5 解決、継承、置き場所

- **探す順**: 引数に直接書かれたオブジェクト → `--platform-file <パス>` → 利用者の設定ディレクトリ `cybersprite/platforms/*.json` → プラグイン（エントリポイント群 `cybersprite.platforms`）→ 内蔵（`src/cybersprite/data/platforms/*.json`）。
- **継承**: 定義ファイルは `extends: "<id>"` を 1 つ持てる。オブジェクトは深く併合し、配列は置き換え、`null` は「定めない」に戻す。循環は `E_INVALID_ARGS`。
- **部分指定**: `--platform nds/sprite-80` のほか、`--platform nds`（表示系だけ。`asset` は `--size` から `custom` として作る）、`--platform free --size 48x48` を認める。
- **既定**: `config.toml` の `[defaults] platform = "<id>"`。`new` が `--platform` なしで呼ばれたときに使う。設定はツール引数から変えられない（§9.6 のまま）。
- **解決の結果はスナップショット**として `project.json` に入る。以後、定義ファイルは読まない。

#### 3.1.6 プラットフォームが駆動するもの

申し送り 2 の 6 項目との対応。

| 申し送りの項目 | 仕組み |
|---|---|
| `new` の既定キャンバス | `asset.canvas`、`defaults.grid`、`defaults.palette` |
| タイルの既定の大きさ | `system.tile`。`add_tileset` と `tileset_from_layer` の既定値になる |
| パレットの色数の予算 | `asset.colors` を、適用時に `project.validation` の `palette_max` と `colors_per_frame_max` へ**書き写す** |
| プレビューと書き出しの既定の倍率 | `defaults.preview`、`defaults.export` |
| 検証の水準 | `platform.validation`（しきい値と `severity`）の書き写しと、新しい規則 Q-PLT |
| 手順書と粒度ガイドの注入 | `workflow` と `craft` から作る短い案内文。`get_info` と `platforms show --guide` が返す（§3.1.8） |

- **書き写しにする理由。** `validation` のキーは「既定値でも必ず書く」（§5.2.2）。層を重ねて動的に解決するより、適用時に書き写して、変えたキーを結果に列挙するほうが、正本を読めば設定が分かる。
- **取り込みパイプライン**も駆動する。`import_image` が `preset` と `pipeline` を省略したら `defaults.pipeline` を使う。`color.bits` があれば、量子化の段（§11.5）で、表せる色にパレットを丸める。量子化は取り込み時の 1 回だけ、という原則 2 の中に収まる。

#### 3.1.7 検証規則

**制約（Q-PLT）。** `platform` が無いプロジェクトでは、どれも走らない。水準は `validation.severity` で変えられる。

| ID | 既定の水準 | 内容 | 段階 |
|---|---|---|---|
| Q-PLT-01 | error | キャンバスが `asset.canvas` と違う（`fixed` のとき）。役割が `background` で `system.screen` より小さい、または `tile.map_max` を超える | 1 |
| Q-PLT-02 | error | パレットに、`color.bits` で表せない色、または `master_palette` にない色がある。該当の番号と、最も近い表せる色を `where` に入れる | 1 |
| Q-PLT-03 | error | `alpha: "binary"` なのに、半透明のパレット色か、255 未満の不透明度がある | 1 |
| Q-PLT-04 | error | パレットの行の違反。1 単位（`palette.unit`）の画素が 2 つ以上の行にまたがる。または、行の先頭（`slot0` が `transparent` / `shared` の行の、透明インデックス以外の先頭）を画素が使っている | 2 |
| Q-PLT-05 | warning | キャンバス、スライス、セルが、`tile` の倍数や `object.sizes` に合わない | 1 |
| Q-PLT-06 | warning | ユニークなタイルの数が `tile.unique_max` を超える。数は `tile.flips` で同じとみなせるものを 1 つに数える | 2 |
| Q-PLT-07 | info | 表示時間が `animation.tick` の割り振りから 1 ms を超えてずれている | 1 |
| Q-PLT-08 | info | `animation.tags` のタグがない。フレーム数が `frames_max` を超える | 1 |

検証報告の `metrics.platform` に、`id`、不透明色の最大数、表せない色の数、ユニークなタイルの数（反転を考慮する場合としない場合）、`tick` からずれたフレームの数を、判定の有無によらず常に入れる。

**色を合わせる Op。** Q-PLT-02 を直すために `conform_palette`（種別 `mutate`、冪等性 I）を足す。パレットの各色を、最も近い表せる色（付録 B の距離）に**明示的に**置き換え、変えた色の前後を結果に並べる。予行で確かめてから使う。編集で色を黙って近似する経路は作らない（原則 2）。

**作法（Q-CRF）。** 既定の水準は `info` で固定の 1 規則だけにする。

| ID | 既定の水準 | 内容 |
|---|---|---|
| Q-CRF-01 | info | `craft` の範囲から外れた指標がある。指標ごとに 1 件、範囲と実測値を出す |

`craft` のキー（どれも `[最小, 最大]` か `null`）:

| キー | 意味 | 測り方 |
|---|---|---|
| `fill_permille` | 不透明ピクセル ÷ キャンバス | 千分率 |
| `depth_max` | 輪郭からの最大の深さ | 透明からの 4 近傍の距離の最大 |
| `flat_permille` | 3×3 が 1 色だけの画素の割合 | 千分率 |
| `region_density_x100` | 同色の連結領域の数 ÷ 不透明ピクセル × 100 | 4 近傍 |
| `ramp_steps` | 1 つの素材の陰影の段数 | `palette.ramps`（H-16）があるときだけ |
| `outline.dark_permille` | 輪郭の画素のうち、最も暗い色の割合 | 千分率 |
| `parts` | 部品どうしの寸法比。例 `"eye.near.w/head.w": [250, 400]` | 名前が `part.` で始まるスライスの矩形から計算する |

`basis` は `authored`（自分たちで書いた一般則）か `measured`（測った値）。`measured` のときは `corpus` に、測った集合の名前、点数、入力一覧のハッシュを入れる。ファイルのパスは入れない。

**作法の指標は関門にしない。** §2.2 のとおり、全体の指標はモクリと参照を決定的には分けなかった。部品の比（目と頭）は 1 例で差が出たが、1 例である。しきい値として使えるかは、発注者が選んだ参照の集合で確かめてから決める。用途は、人間が見るときの手がかりと、作り手が設計の段階で照合する物差しである。

#### 3.1.10 実機向けの書き出し（段階 2）

- `export_native`（種別 E）。引数は `format`、`out`、`tileset` または `layer`、`palette_out`、`map_out`。書き出しの拡張点（§15.1 の `cybersprite.exporters`）に乗せる。この拡張点は今は実装されていない（R1-04）。
- 自己検査（§8.8）のため、どの形式も復号器を持つ。書いたバイト列を復号し、レンダラの結果とタイル単位で照合する。
- 形式の定義は、公開されている機種の資料の「事実」から自分たちで書き、テストベクタ（`tests/vectors/native/`）で固定する。最初は `gb-2bpp`。例として定義を書く。
  - タイル 1 枚は 16 バイト。行 `r`（上から 0〜7）は、バイト `2r`（下位のビット面）とバイト `2r + 1`（上位のビット面）。
  - 行の中の画素 `x`（左から 0〜7）は、各バイトのビット `7 − x`。画素の値は `下位ビット + 2 × 上位ビット`（0〜3）。
  - パレット番号から値への対応は、行の中での位置である。`slot0` が `transparent` か `shared` なら `値 = 番号 mod row_size`。`slot0` が `color`（透明を持たない背景）なら、透明インデックスを画素が使っていないことを Q-PLT-04 で確かめたうえで、`値 = (番号 − 1) mod row_size`。
- 走査線あたりのスプライト数や VRAM の割り当ては、実行時の事情なので検証しない（§1.3 の非目的「ゲームエンジン」）。`system.object.notes` に参考として書くだけにする。

### 3.2 DS 粒度の制作は現実に回るか（申し送り 1。H-12〜H-18）

**結論: 道具としては回る。質は回っていない。** 描画、書き出し、検証は 80×80 でも信頼できた（DS 報告と、こちらの再実行で確認）。足りないのは §2.4 の 5 点で、うち Op と性能に関するものをここに書く。

#### 3.2.1 部分アニメーション（第 5 世代式）への対応

| 要素 | いまの対応 | 判断 |
|---|---|---|
| 部品ごとの平行移動（上下動、遅れ） | レイヤーとセルの位置でできる。ただしリンクセルの位置が共有で、罠になる（R1-05） | **直す**（H-12） |
| 少数のユニークなコマの並べ替え | `add_frame cels=link copy_from=n` で、同じコマを何度でも置ける。シートは `--merge-duplicates` で 1 つにまとまる | できる。手順書に書く |
| 1 枚の絵を、位置だけ変えて使い回す | できない。リンクは位置も共有する（§5.6.3）。位置を変えるにはリンクを切るしかなく、絵が複製される。あとで絵を直すとき、全部の複製を直すことになる | **仕様を拡張する**（H-12 の後半） |
| 部品の回転と拡大縮小 | できない。整数幾何だけ、という原則 3 による | **対応しない。** 回転した部品は描き直す。`transform_region` の 90 度回転と反転は使える |

**H-12 `set_cel` とリンク。**

- すぐ直す分: `set_cel` に `linked`（`"error"` / `"all"` / `"unlink"`、既定 `"error"`）を足す。リンクの組に属するセルの `x` `y` `opacity` を変えようとして `linked` が既定のままなら、`E_LINKED_CEL` を返す。詳細に `linked_frames` を入れ、ヒントに 2 つの選択肢を書く。
- 相対移動は、Codex の案の `move_cel`（`dx`、`dy`、必須の `scope`: `"frame"` / `"shared"`）を新しい Op として足す。`set_cel` に `dx` / `dy` を足すより良い。`set_cel` の冪等性（I）を崩さずに済む。
- Codex は、`set_cel` の既定をエラーに変えることには反対で、警告にとどめる案である。私は、エラーにする案を維持する。DS の試作では、結果に `linked_frames` が出ていたのに、作り手が気づいたのはプレビューを見たときだった。警告も同じように読み飛ばされる。1.0 の公開前なので、互換性の負担もない（§3.8 の不一致 2）。
- 仕様の拡張: リンクセルに省略可の `dx` / `dy`（既定 0）を持たせる。描く位置は「持ち主の位置 ＋ (dx, dy)」。絵は 1 つのまま、フレームごとに位置を変えられる。`.aseprite` に書くときは、ずれのあるリンクを独立したセルとして書く。読むときは、同じレイヤーで画素が一致するセルを、ずれつきのリンクとして取り込む。往復の一致（§5.9.2）はこれで保てる。

#### 3.2.2 図形に頼らない成形のための Op

| 番号 | 追加 | 定義 |
|---|---|---|
| H-13 | 保護描画 | 描画の Op すべてに、省略可の `mask: {only_on, not_on, region}` を足す。`only_on` / `not_on` は色の配列で、**描く前の**対象セルの画素で判定する。`region` は §6.4.9 の領域。「影の色の上にだけ、基本色を塗る」が 1 回でできる |
| H-13 | 領域の形 | §6.4.9 に `ellipse`（§6.4.5 の内部判定）、`polygon`（§6.4.6 の塗りつぶし）、組み合わせ `{"type": "and" / "or" / "not", "of": […]}` を足す |
| H-14 | 冪等な輪郭 | `outline` に `exclude_colors`（色の配列。集合 `A` から除く）を足す。輪郭の色自身を入れると、同じ呼び出しの 2 回目は何も変えない。部位を足すたびに輪郭が太る問題と、輪郭のためだけにレイヤーを分ける必要がなくなる |
| H-15 | プレビューの切り出し | `render_preview` に `rect: {x, y, w, h}` を足す。80×80 の顔だけを大きく見られる |
| H-16 | 色の名前 | 色を受ける引数が `"@<名前>"`（`palette.names` の名前）を受ける。同じ名前が 2 つあれば `E_AMBIGUOUS_REF`。`draw_rows` の `sym` に、文字から色への対応表 `legend` を足す |
| H-16 | ランプ | `palette.ramps`（省略可）: `[{"name": "body", "indices": [3, 4, 7, 10]}]`。暗い順。`"@body:0"` で最も暗い色を指せる。`shift_ramp`（領域内の画素を、ランプの中で 1 段明るく、または暗くする）と、選択的な輪郭（隣の素材のランプの最も暗い色で縁を取る）の土台になる |
| H-17 | 検証デルタの点の差分 | `Q-PIX-01` / `Q-PIX-02` に限り、デルタに `resolved_points` と `new_points` を入れる。`where.layer` を埋める |
| H-18 | 置き換えの適用 | `apply --replace-last`: 直前のトランザクションを取り消し、新しいものを適用するまでを 1 回で行う。DS 制作で 6 回あった「取り消し → 直す → 再適用」を、履歴の上でも 1 手にする（優先度は低い） |

DS 報告 §6 のうち、すでに解消しているものもある（実行で確認）。横並びのプレビュー（`--layout strip` / `grid`）、複数フレームの `--out` のエラー文、セルの原点の表示（`info --include layers` に矩形とリンク元が出る）、1 回の呼び出しの時間（当時 4.7 秒、いま 1〜1.5 秒）。

#### 3.2.3 大きさと速さ（実測）

`csp.exe` を直接呼び、3 回の最小値を取った。調査フォークが同時に動いていたので、絶対値は遅めである。

| プロジェクト | `project.json` | 1 ピクセルの変更（プレビューなし） | `validate` | 横並びのプレビュー | シートの書き出し |
|---|---|---|---|---|---|
| 32×32、3 層、4 フレーム | 26 KB | 1.4 秒 | 1.0 秒 | 0.9 秒 | 1.0 秒 |
| 96×96、8 層、45 フレーム、全セルが独立で密 | 6.4 MB | 2.9 秒 | 3.8 秒 | 2.3 秒 | 2.7 秒 |
| 480×270、4 層、1 フレーム、密 | 1.0 MB | 3.0 秒 | 1.8 秒 | 1.3 秒 | 1.8 秒 |

- 起動（`--version`）は 0.33 秒。小さなプロジェクトでも 1 回あたり約 1 秒かかるのは、Op の読み込みなど、起動後の固定費である。
- 96×96・45 フレームの 720 個の Op を 1 つのトランザクションで適用するのに、29.7 秒かかった。
- モクリの実物は 57 KB（リンクが効いている）なので、リンクを使う限り DS 級は「小さなプロジェクト」の側にいる。全コマを描き分ける 45 フレームや、480×270 の背景は 2〜4 秒の側に入る。
- MCP の常駐で速くなる、という期待は、現状では成り立たない。MCP の 1 回は、同じ処理の直接の呼び出しの約 5 倍かかる（R1-07）。

**方針**（R1-07、R1-09）: MCP の期限検査を直す。CLI は Op の読み込みを遅らせる。大きな正本は、`.cybersprite/cache/` に内容ハッシュをキーにした派生キャッシュ（復号済みのセル、フレーム単位の検証結果）を持つ。§13.4 はフレーム単位のキャッシュを認めている。§13.8 の目標に「CLI の 1 回の端から端まで」と「96×96・8 層・45 フレーム」の行を足す。

### 3.3 DM 知見への回答（申し送り 3。H-07〜H-10）

#### 3.3.1 極小の制約で破綻する（知見 1、6）

16×16・3 色では「描く力」より「制約の下で設計する力」が要る、という見立てに同意する。道具ができることは 4 つ。

1. **制約を宣言できる。** `dmg/sprite-16`（§3.1.11）で、3 色、8×8 のタイル、色表が検証に入る。
2. **手順 `silhouette-first`。** 1 色でシルエットだけを作る → 4 方向を並べて見る → 2 色目で内側の切れ目（顔、腕）→ 3 色目。各段でレビューシートを出す。
3. **たくさん作って、人間が選ぶ。** 16×16 は 1 案が安い。シルエットの段階で 8〜12 案を 1 枚に並べ、利用者が選ぶ。極小では、これがいちばん効くと考える。
4. **数えられるものは数える。** 4 方向のコマどうしの画素の違い（少ないほど方向が見分けにくい）、色ごとの面積の割合、輪郭に占める最も暗い色の割合、ユニークなタイルの数。どれも `metrics.platform` と `craft` に出す。合否には使わない。

正直に書くと、**これで協力者の手描きの水準に届く保証はない。** 道具が保証できるのは、制約を破らないことと、人間が早い段階で見て選べることまでである。

#### 3.3.2 自己評価は人間の目とずれる（知見 3）

モクリで実証された。仕組みと規則の両方で対処する。

**H-07 完了条件に、人間が見る関門を足す**（§13.7、`AGENTS.md` §6.3）。

- 関門は 3 か所。(1) 設計が決まったとき（原画）、(2) ブロッキングが済んだとき（シルエットと顔。×1 で読めるか）、(3) 仕上げの前。
- 対話できるとき: レビューシートを見せ、返事を待つ。
- 対話できない自律タスク: シートを書き出して先へ進み、最終報告に 3 枚とも載せる。
- 小さな題材（`workflow: "direct"`）では (2) と (3) を 1 回にまとめてよい。

**H-08 レビューシート**（`render_preview` の `layout: "review"`）。1 枚の PNG に次を並べる。装飾なので、書き出しには入らない。

1. ×1 の実寸。`defaults.preview.backgrounds` の背景ごとに 1 つ。`system.screen` があれば、その大きさの枠の中に置く。
2. 整数倍の拡大（`defaults.export.review_scale`）。
3. シルエット（不透明な画素を 1 色で塗ったもの）。
4. 明るさだけの版（パレットの色を、付録 B の明度で灰色に直したもの）。
5. 原画や参照があれば、同じ倍率で横に置く（H-11）。
6. アニメーションなら、タグの再生順の横並び。

**H-09 報告の規則**（`skills/validate-export`、`AGENTS.md` §6.3）。

- 見た目の点数や「きれいにできた」を、品質の根拠として書かない。書くのは、プラットフォームとの照合の表、レビューシートのパス、**自分で疑っている箇所を 3 つ**。
- 使い心地の点数は、道具への意見として別の欄に書く。
- 複数の案を見せるときは、順位を付けずに並べる。推す案があるなら、理由は 1 行まで。
- 「改善」のたびに、前後を並べた 1 枚を残す。前の版のリビジョン番号を報告に書き、人間が戻せるようにする。

#### 3.3.3 実ソフトのタイルデータを解析して資料にする（知見 7）

**設計は可能で、価値もある。条件を 4 つ付ける。**

**H-10 `analyze`（段階 2）。** 利用者が用意した画像やタイルの生データから統計を取り、`craft` の JSON を出す。

1. **出力は統計だけ。** 画像を書き出す機能を持たせない。出力に入れるのは数値、入力一覧のハッシュ、利用者のメモ。
2. **置き場所は利用者の手元。** 結果は設定ディレクトリの `platforms/` に入る。リポジトリ、配布物、内蔵プリセットには入れない。内蔵の `craft` は `authored` だけにする。測った数値は著作物そのものではないが、公開する OSS に特定の市販タイトル由来の値を載せるかは、発注者の判断にしたい（§6 の 1）。
3. **入力は利用者が正規に持っているもの。** ROM の入れ物の解析や展開はしない。受け取るのは、画像と、タイルの生のバイト列（位置と長さは利用者が指定する）。復号器は実機向けの書き出し（§3.1.10）の自己検査用と同じものを使う。DM で共有された市販 ROM は、申し送りのとおり使わない。
4. **限界を知っておく。** タイルの集まりには、組み立ての情報がない。取れるのは質感の作法（階調の使い分け、かたまりの大きさ、ディザの有無、タイルの使い回しの率）までである。**目と頭の比のような設計の作法は取れない。** そちらは、組み上がったスプライトに部品の矩形（`part.` のスライス）を付けて測る。モクリの敗因は後者なので、タイル解析だけでは目は直らない。

法的な評価は私の専門外である。公開や商用の前に、専門家の確認を勧める（台帳 L-08 と同じ扱い）。

### 3.4 制作の分担と標準ワークフロー（申し送り 5。H-11、H-19）

**H-19 分担を文書に入れる。** `docs/SPEC.md` §16.2、`AGENTS.md` §5.1、`skills/` に、次を明記する。いま `skills/` に imagegen への言及は 1 つもない（実行: 検索で 0 件）。

- 原案の生成（通常の三面図、ピクセルアート風の三面図）は Codex の imagegen。
- 解釈、ドットを打つこと、見た目の判断は Opus。
- 従来の規則「ビジュアルの判断は Opus」は変わらない。切り出したのは原案の生成だけである。

**H-11 設計原画の経路。**

- `add_source`（新規、種別 `ingest`）: 画像を、キャンバスに入れずに `source/` へ来歴つきで登録する。来歴に `use: "design"` を足す（パイプラインの入力は `"canvas"`）。いまは、配置を伴う `import_image` しか入口がない。
- `render_preview` に `guide: {source, file, x, y, scale, mode}` を足す。`mode: "side"` は、原画を同じ倍率で横に並べる。原画は**プレビューの装飾**であり、正本のピクセルにもパレットにも入らない。原画の色でパレットを汚さずに済む。
- 重ねて透かす表示（`mode: "under"`）と、GUI での表示は v1.x。

**手順書 `skills/workflows/turnaround-parts.md`（新規）の骨子。**

| 段 | 担当 | すること | 関門 |
|---|---|---|---|
| 0 | Opus | プラットフォームを決め、案内文を読む。参照があれば計測値を読む（§3.5） | |
| 1 | Codex | 通常の三面図（正面、側面、背面）を生成する。`add_source` で登録する | (1) 設計 |
| 2 | Codex | 1 をもとに、ピクセルアート風の三面図を生成する。粒度と色は最終形に寄せきらない。登録する | |
| 3a | Opus | 向きごとに、原画を横に並べたプレビューを見ながら、1 色でシルエットを作る。顔を先に決める（目の寸法を `craft.parts` と照合する） | (2) ブロッキング |
| 3b | Opus | 部品をレイヤーに分ける。色面 → 影（原画の影の「形」を拾う）→ 輪郭 → 行データで仕上げ | (3) 仕上げ前 |
| 4 | Opus | 向きとコマをフレームとタグにまとめる。動きを付ける（`animate`） | |
| 5 | Opus | 検証、書き出し、書き出したファイルの確認（`validate-export`） | |

- 3 の別の道として、2 の画像を変換パイプラインで取り込み、手で直す方法もある。**どちらが良いかは、まだ分からない。** 定期の e2e で両方を作り、発注者が見て決めるのがよい。
- 生成への指示は、否定形ではなく肯定形で書く（DM 知見 5）。青い背景のクロマキーは、青い絵柄が抜けることがある。背景の色は題材と離れた色を選ぶ、と `import-convert` に書く。
- **前提が未検証である。** 実際の生成画像は、まだ 1 枚もパイプラインを通っていない（R1-06）。この手順の最初の入口なので、追加マイルストーンの最初に置く。

### 3.5 参照ライブラリと資料サイトのコネクタ（申し送り 6。H-20）

**ライブラリの設計には賛成する。コネクタの取得方法は推奨しない。** 分けて書く。

**H-20 参照の規律を仕様にする**（`docs/SPEC.md` §3 に節を足す）。いまの §3 は他のエディタ製品との関係しか定めておらず、ゲームの実スプライトを参照する運用が、仕様にも参照ログにも無い（R1-11）。§3.1 の「他製品のスプライトを使わない」と文字の上でぶつかっている。

- **置き場所**: リポジトリの外か `_private/refs-library/`。**プロジェクトの `source/` には入れない**（プロジェクトは作例として公開されうる）。プロジェクトに残してよいのは、参照の ID、ハッシュ、計測値だけ。
- **してよいこと**: 計測と、自分の言葉での所見。
- **してはならないこと**: なぞること、画素を書き写すこと、1 つのスプライトのパレットをそのまま使うこと、既存のキャラクターに似せること。レビューシートに参照を並べたものは `.cybersprite/previews/` の中だけに置く。
- **記録**: `docs/reference/PROVENANCE_LOG.md` に、資料と得た事実を 1 行。DS 特別テストの分は、さかのぼって書く。
- **追跡する文書に載せてよいもの**: 統計値まで。題名や画像は載せない（この文書もそうしている）。
- **手順書の書き方**: 「参照ライブラリ（ディレクトリと `manifest.jsonl`）に画像があれば、計測して `craft` に反映する」とだけ書く。取得の手段には触れない。コネクタ本体を公開リポジトリに入れない、という申し送りの方針のままでよい。

**コネクタについての率直な見解。**

- この道具は、サイトが自動の取得を 403 で断っているのを、実ブラウザを経由して通す作りになっている。申し送りの規律（必要なときだけ、少量、非公開）は負荷と露出を小さくするが、断られている取得を通す、という性質は変わらない。サイトの利用条件に反する可能性が高い。置かれている素材の権利も、元のゲーム会社にある。
- 上流として、これを標準の手順に組み込むことは勧めない。**人がブラウザで見て保存したものをライブラリに入れる運用を標準**にし、コネクタを使い続けるかは発注者が決める、という線を提案する（§6 の 2）。
- もう 1 点。参照の画像を、imagegen の画像入力として渡すと、出力が元の絵に近づく危険が上がる。imagegen に渡すのは文章の指示と計測値にとどめることを勧める（§6 の 3）。

### 3.6 GPU 環境での生成入力の拡張（申し送り 7。H-21）

**大枠は、すでに仕様にある**（§12.4、§12.5、§2.4）。重みは同梱しない。設定ファイルでの登録、ライセンス名の承諾、ハッシュの記録、LoRA とベースの別記録がある。足すのは 4 点。

1. **登録の項目。** `[generators.diffusers.models.<名前>]` に、`kind`（`diffusers-dir` / `checkpoint` / `lora`）、`base_model`、`local_path`、`license`、`license_url`、`commercial_use`（`"yes"` / `"no"` / `"unknown"`）、`note` を持たせる。ハッシュは登録時に計算する。登録は設定ファイルと、人間が使う CLI（`gen register-model`）だけで行う。MCP には出さない（§9.6）。
2. **2 つの出口。** `generate_image` に `use`（`"design"` / `"canvas"`、既定 `"canvas"`）を足し、来歴に記録する。`design` は §3.4 の原画の経路（プレビューに並べる）へ、`canvas` は `import_image source=SRC<n>` へつなぐ。どちらもキャンバスには直接入らない（§12.1 のまま）。
3. **利用条件を検証に出す。** `Q-SRC-04`（warning）: 配置済みのソースのモデルかアダプタの `commercial_use` が `"yes"` でない。公開や商用の前に気づける。道具は重みの適法性を保証しない、という立場は変えない。
4. **前提の作業。** `diffusers` extra の依存の監査（I-014）と、実 GPU での生成の確認を、追加マイルストーンに入れる。CI に GPU は無いので、発注者の PC での手動の確認とし、結果を `docs/GENERATION.md` に記録する。実装は今、ローカルにある実体だけを受け付ける（I-703）。安全な判断なので、仕様のほうを合わせる（R1-14）。

### 3.7 ComfyUI 互換（申し送り 8。H-22）

**線引き: 段階 1 と 2 はやる。段階 3 はやらない。**

申し送りのとおり、本体は GPL-3.0 なので組み込まない。§12.2 も「利用者が起動した ComfyUI を HTTP で呼ぶ。v1.x のプラグイン」としており、方針は一致している。クリーンルームの面では、**参照してよいのは公開されている API の文書と、動かして見える挙動だけ**である。ソースコードは開かない（§3.1）。

| 段階 | 内容 | 判断 |
|---|---|---|
| 1. API バックエンド | 生成バックエンド `comfyui` を、拡張点 `cybersprite.generators` に足す。利用者が起動しているサーバに、API 形式のワークフローを送り、できた画像を受け取る。通信は標準ライブラリで足り、依存は増えない。サーバの URL は設定ファイルでだけ決める。既定は `127.0.0.1`。起動していなければ `availability` が理由を返す | **やる** |
| 2. ワークフローの登録と対応付け | 利用者のワークフロー JSON を、設定に名前を付けて登録する。CyberSprite のパラメータ（プロンプト、シード、幅、高さ、チェックポイント、LoRA）と、ノードの入力との対応を、**明示的に**書く（下の例）。補助として、ノードの種類から対応の案を出す `gen comfy-inspect <ファイル>` を用意し、人間が確かめて設定に書く | **やる** |
| 3. ノードの互換 | ノードグラフの再実装、他者のワークフローやノードの同梱 | **やらない。** 手順書に、推奨の組み方を文章で書くにとどめる。取り込み側の工夫（升目の検出など）は、変換パイプラインのステップとして別に扱う |

```toml
[generators.comfyui]
url = "http://127.0.0.1:8188"

[generators.comfyui.workflows.pixel-turnaround]
file = "C:/comfy/workflows/pixel_turnaround_api.json"
license = "checkpoint: <名前>; lora: <名前>"
commercial_use = "unknown"

[generators.comfyui.workflows.pixel-turnaround.bind]
prompt = ["6", "inputs", "text"]
negative_prompt = ["7", "inputs", "text"]
seed = ["3", "inputs", "seed"]
width = ["5", "inputs", "width"]
height = ["5", "inputs", "height"]
```

- **安全。** カスタムノードは、サーバの上で任意のコードを動かせる。エージェントがツールの引数で任意のワークフローを送れてはならない。選べるのは、設定に登録された名前だけ。引数で変えられるのは、対応付けたパラメータだけ（§9.6、§10.1.2 と同じ考え方）。
- **来歴。** 値を埋めた後のワークフロー全体を `source/SRC<n>/workflow.json` に保存し、ハッシュ、サーバの URL、シード、パラメータを記録する。サーバの中にある重みのライセンスを、CyberSprite は知ることができない。そのため `license` は登録時の必須項目とし、承諾はワークフローのファイルのハッシュに結び付ける。
- **順番。** 段階 1 は軽い。ただし、先に §3.6 の実 GPU での確認が要る。

2. **資料サイトのコネクタを使い続けるか。** 推奨: 人が保存したものをライブラリに入れる運用を標準にする（§3.5）。
3. **参照の画像を、imagegen の画像入力として渡すか。** 推奨: 渡さない。文章と計測値にとどめる（§3.5）。
4. **ライセンスの例外 2 件の事後の承認。** I-010（`pathspec`、MPL-2.0、ビルド時だけ）と I-012（`pywin32` に同梱の LGPL の部品。`mcp` extra の Windows での推移的依存）は、オーケストレーターの判断で通っている。Codex は「発注者の判断が要る」と保留していた。私の見立てでは方針（§2.1）の趣旨に反しないが、本文に例外として明記されていない（R1-22）。
5. **「256 px 級」の意味。** 1 コマの大きさか、シート全体の大きさか（§3.1.9）。
6. **範囲。** M11 と M12 を 1.0 に入れることを勧める。M13 を 1.0 に入れるか、1.x に送るか。
7. **2 つのレビューの違い。** 重大度の違い 2 点と、設計の不一致 3 点（§3.8）。
