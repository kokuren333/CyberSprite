# 性能測定

## M3: CLI 起動（2026-11-12）

- Windows 11（10.0.26200）、CPython 3.12.10、uv の仮想環境。
- `uv run python tools/measure_cli_startup.py`。インストール済みの
  `.venv/Scripts/cybersprite.EXE` を各 7 回起動し、親プロセスの単調時計で起動から終了まで測定した。
  uv 自体の起動・同期時間は含めない。整数 ms への切り捨て。
- 独立した `python -X importtime -m cybersprite --version/--help` で import も検査した。
  **NumPy、pydantic、Pillow、aseprite の import は両方とも 0 件**。

| コマンド | 7 回の測定（ms） | 中央値 | 最大値 | 400 ms の目標 |
|---|---|---|---|---|
| `cybersprite --version` | 218, 266, 253, 246, 222, 257, 244 | 246 ms | 266 ms | 達成 |
| `cybersprite --help` | 234, 254, 269, 274, 267, 290, 240 | 267 ms | 290 ms | 達成 |

全体テスト終了後の測定値。同じコードでも、全体テストなどが動いていた回は
version が 438〜780 ms（中央値 505 ms）、help が 428〜527 ms（中央値 484 ms）だった。
負荷・ファイル I/O 競合の影響と推定するが、原因を個別に計測したものではない。
負荷のある環境で常に 400 ms 以下になる保証はしない。

切り分け用の 7 回測定では、何もしない Python が中央値 56 ms、
`python -m cybersprite --version` が 202 ms、実行ファイル版が 214 ms。
そのときの importtime は `cybersprite.cli` の累積 102,700 μs
（うち Click の累積 67,011 μs）。最上位ヘルプはスキーマ生成やレジストリ初期化を行わない。

Linux の実測は未実施（I-007）。他の性能目標は担当マイルストーンで追記する。

## M6 組み込み変換（2026-11-12）

Windows、Python 3.12.10、NumPy 2.3.4、Pillow 13.0.0。再実行は `uv run python tools/benchmark_pipeline.py`。

| 入力・設定 | 測定範囲 | 3 回の時間 | 目標 |
|---|---|---|---|
| 1024×1024 PNG、元作品を4×4に並べ16倍、upscaled → 64×64 | 復号、グリッド、縮小、量子化、後始末、指標・関門、報告、stored 圧縮の全段階 PNG、最終 PNG、各 PNG の復号検証 | 805 / 1133 / 656 ms | 5000 ms 以内（全回達成） |

プロセスの起動と入力ファイルの作成は含めない。ディスクへの段階画像と報告の保存は含む。平均 865 ms、中央値 805 ms。無作為な写真・多数フレーム・全設定の上限時間を保証する測定ではない。

均等セルの純度と center 縮小は配列で計算し、色割当は異なる RGB ごとに整数 Oklab 距離を計算する。距離行列は4096色ずつ処理してメモリを制限する。孤立ピクセルは8方向の整数配列比較で数える。これらの経路は既存ベクタとコーパスの画素一致で検査する。

## M10: 全目標の測定（2026-11-12）

開発機: Windows 11 10.0.26200、Intel Core i7-1185G7 3.00GHz（4コア / 8論理CPU）、RAM 16,983,785,472 bytes、CPython 3.12.10、NumPy 2.3.4、Pillow 13.0.0、uv 0.12.23。GUI buildはNode 24.15.0 / npm 11.12.1。Windowsのローカル作業ディレクトリで測定した。Linuxの実測は未実施（I-007）。

再現: `uv sync --locked --extra mcp --extra gui` → `uv run python -m tools.bench --out build/m10-bench-final.json`。各3回、単調時計 `perf_counter_ns`、μsの整数をJSONへ記録する。以下は全体テスト終了後の一連の測定。中央値で比較し、最大値も併記する。実行時の他アプリ・OS負荷まで固定した測定ではない。

|---|---|---|---|---|---|

| 64×64・10層・32フレーム、1トランザクション、プレビュー込み | 1283.689 / 1903.323 / 1654.159 | 1654.159 | 1903.323 | 150 | 未達 |

| 1024×1024・組み込み変換 | 411.841 / 487.240 / 464.683 | 464.683 | 487.240 | 5000 | 達成 |

測定境界と入力:

- CLIだけプロセス起動から終了までを含み、uvの起動・同期は含めない。他はimport・fixtureの初期作成・サーバ起動を除く。初期fixtureは排他作成し、以後の正本変更は登録Opだけを通る。
- fixtureは2色を8px角で交互に置いた密な画像。全層・全フレームに独立した全サイズのセルを持ち、フレームは同じ内容である。空プロジェクトではないが、任意の画風・すべて異なるフレームの上限値を測る試験でもない。
- トランザクションは最上層・フレーム0の1点を交互に変更する。読込・複製・正規化・前後の全体検証・差分・履歴と正本の保存・変更プレビューPNGを含む。プレビューは既定の整数拡大。
- renderはメモリ上のcore renderだけ。validateは全構造と全品質規則・指標を含み、関門やルールを無効にしていない。同一合成入力の連続フレームは呼出し内の直前1件を再利用する。
- GUIは実Uvicorn / WebSocketで `op.apply(set_pixel, preview=none)` → `render.frame` を実行する。検証と保存、通知、RGBA base64応答を含む。ブラウザのpointer-upからCanvas描画までの実測ではなく、描画側の追加時間は含めない。
- pipelineは同じ格子画像64×64を整数16倍した1024×1024 PNG。`upscaled` の全組み込み処理、復号、関門、段階PNG・報告・最終PNGのディスク保存と読戻し検証を含む。写真や百万種類の色の量子化時間は保証しない。

### 最適化と残った未達

初回測定の中央値はトランザクション6666.419ms、全体検証16158.864ms、GUI523.948ms。負荷条件も異なるため、厳密に統制した速度比としては扱わない。プロファイルでは、構造検証で各文字にPythonの `ord` を呼ぶ検査と各画素の16進数解析、全フレームの再描画・クラスタ探索が目立った。

M10では、サロゲート検出を同じ範囲の正規表現にし、画素行の正常系をbytesによる検査へ変更した。不正画素は従来どおり最初の座標を返す。クラスタの比較をPython整数とbytearrayへ移し、種の行優先順と幅優先の近傍順を維持した。合成入力を厳密な不変タプルで比較し、同じフレームのreport内再利用と、前後で同一入力の差分描画の省略を加えた。永続キャッシュ・近似ハッシュ・新規依存はない。固定シード50配列の旧探索との比較、キャッシュなし全量reportとの比較、合成入力変更の失効試験、既存全ゴールデンで出力不変を確認した。

残る対策:

| 未達 | 原因 | 次の対策 |
|---|---|---|
| 150msのトランザクション | 320個の密なセルを持つ正本全体の読込、再検証、複製、正準JSON・gzipスナップショットの生成を1点編集でも繰り返す。Windowsの複数ファイルの原子的保存も含む | 1トランザクション内で検証済み正準bytesを履歴にも共有し、同じモデルの構造検証を重複させない設計にする。変更セルを根拠に再計算範囲を限定し、全量validateとのデルタ同値試験を維持する |
| 50msのGUI反映 | 同期的な検証・複製・履歴保存、全画像のRGBA再取得を含む。ブラウザを除いた今回の往復だけでも50msを超える | サーバ側で検証・保存・描画・転送を区間別に計測する。上記の保存経路改善と変更領域のRGBA配信を進め、最後にブラウザのpointer-upから描画完了までを別途測る |

未達を隠して目標を変更しない。§13.8の方針どおり、目標未達だけをリリース停止理由にはせず、[KNOWN_ISSUES.md](KNOWN_ISSUES.md)にも記録する。
