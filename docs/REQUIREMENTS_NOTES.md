### 2.1 Aseprite（プロプライエタリ、EULA。参照のみ）

参照したもの: 公開のファイル形式仕様、CLI 文書、利用者向け文書の目次と一部のページ（タイルマップ、レイヤー、アニメーション、選択、書き出し、描画、スプライトシート、色）。

| 採ったもの | 理由 | 仕様の節 |
|---|---|---|
| 「スプライト = レイヤー × フレームの格子にセルが置かれる」というモデル | ドット絵アニメーションの事実上の共通語彙であり、エージェントも人間も説明なしで理解できる | §5 |
| リンクセル（複数フレームで同じ画像を共有） | アニメーションで「動かない部分」を 1 か所直せば全フレームに効く。エージェントの修正回数を減らす | §5.6.3 |
| タグ（フレーム範囲の名前、再生方向 4 種、繰り返し回数） | 1 つのファイルに複数のアニメーションを持つための最小の仕組み。ゲームエンジン側の読み込みもこれを前提にしている | §5.7 |
| スライス（9 パッチの中央領域、ピボット、フレームごとのキー） | 当たり判定や UI 部品の切り出しを、絵と同じファイルで管理できる | §5.8.1 |
| タイルマップレイヤーとタイルセット（空タイルは番号 0、3 種の反転フラグ） | 「タイルを 1 枚直すと全配置に反映」という性質が、検証と相性がよい。公開仕様の説明自体が「タイルとパレットは同じ構造」としており、インデックス正本の考え方と揃う | §5.8.2、§6.5.4 |
| インデックスモードの透明インデックスと背景レイヤーの関係 | `.aseprite` との往復に必要 | §5.3.2、§5.5.2 |
| セルごとの Z インデックス | 往復に必要。並べ替え規則は公開仕様の記述（`(レイヤー順 + z, z)` で並べる）をそのまま事実として採った | §6.5.2 |
| ユーザーデータ（テキスト、色、型つきプロパティ） | エージェントやゲーム側が任意の情報を付けられる。型を保つために `$type` の包みを設計した | §5.8.3 |
| CLI の能力の範囲（一括変換、シート、分割、範囲指定、一覧表示） | 「できること」の一覧として最も整っている。コマンド体系は独自に定義し、能力だけを対応させた | §9.5 |
| 画面の大まかな構成（中央にキャンバス、下にタイムライン、横にパレットとツール） | 発注者の指定。一般的なレイアウトの考え方であり、見た目は独自に作る | §14.2 |
| タイルマップの「ピクセルを描く／タイルを置く」の 2 つの編集の区別と、手動・自動・スタックの 3 モードという整理 | 機能の切り分けとして分かりやすい。v1 は手動モード相当だけにし、残りは v1.x | §7.9 |

| 採らなかったもの | 理由 | 仕様の節 |
|---|---|---|
| RGBA とグレースケールの編集モード | 「ピクセルはパレット番号でしか存在できない」という根幹と両立しない。RGBA は取り込み時に量子化し、書き出しはいつでも RGBA にできる、という形で必要を満たす | §1.3、§7.2 |
| フレームごとのパレット変更 | パレットロックと検証を単純に保つため。色を動かす演出は、色を別の番号にして描き分ければ表せる。読み込み時は統合して取り込む | §5.3.2、§5.9.1 |
| 参照レイヤー | RGBA の画像を任意の倍率で置く機能であり、モデルに入れると「インデックスだけ」の保証が崩れる。下絵は GUI の表示機能として `source/` の画像を重ねる形にした（v1.x） | §7.4 |
| Lua スクリプトと拡張パッケージ | エージェントに無制限の実行環境を渡さない。同じ用途は、有界な Op の列（`apply_ops`）と Python プラグインで満たす | §7.12 |
| ぼかし、畳み込みフィルタ、補間つきの拡縮 | パレットにない色を作る。インデックス正本では、結果を最近色に丸めるしかなく、意図しない絵になる | §7.6、§7.8 |
| 「現在のレイヤー」「現在のフレーム」「現在の選択範囲」に依存する操作体系（API として） | 人間には便利だが、エージェントには状態の取り違えの原因になる。API では対象を毎回明示させ、GUI だけが表示状態として持つ | §4.2、§6.4.9 |
| 空のセルの保持 | 「同じ絵は同じ JSON」を優先した。空セルとセルなしの区別は、描画結果に影響しない | §5.6.4 |
| 特定の投稿サービス向けの書き出し調整 | プロダクトの範囲外 | §7.11 |
| ショートカットの一覧表を写すこと | 表そのものは写さない。広く使われている慣例と、発注者が実際に使うキーだけを既定にする | §14.5 |

実機で確かめるべきこと（上流工程では未確認）は、`docs/SPEC.md` §3.5.3（画面 47 件）と §3.5.4（挙動 11 件）に列挙した。

### 2.13 MCP の仕様（2026-07-28 版）

現行の仕様はステートレスであり、「状態が必要なら、明示的なハンドルを引数で受け渡す」ことを勧めている。CyberSprite では、プロジェクトのパスがそのハンドルにあたる。全ツールが `project` を明示し、対象のレイヤーとフレームも毎回明示する設計は、この仕様と素直に合う。ツールの一覧を決まった順で返すこと（プロンプトのキャッシュに効く）、実行エラーをツールの結果として返すこと（モデルが自分で直せる）も、仕様の勧めに従った。

### 2.14 バージョン管理システム（考え方だけ）

「正本はテキストで、差分が読める」「変更は原子的なコミットで、番号が付く」「古い状態に戻すのも新しいコミット」という考え方を、ピクセルの行ごとの文字列（D-02）、リビジョン（D-08）、取り消しの扱い（D-09）に取り入れた。

## 3. 決定記録の理由（D-01〜D-40）

| 番号 | 採った案 | 検討して採らなかった案 | 理由 |
|---|---|---|---|
| D-01 | プロジェクトはディレクトリで、正本は `project.json` | 単一の JSON ファイル。ZIP にまとめた独自形式 | 来歴つきの元画像（`source/`）と、履歴・プレビュー（派生データ）を同じ場所に置く必要がある。ZIP はエージェントが直接読めず、git の差分も読めない |
| D-02 | ピクセルは行ごとの 16 進文字列 | base64、zlib 圧縮 + base64、セルごとの外部 PNG | 行単位の差分が読める。エージェントが JSON を直接読める。圧縮ライブラリの版による出力差が正本に入らない。外部 PNG は「JSON が正本」という方針を弱め、パレットが二重になる。大きさの増加（1 ピクセル 2 バイト）は、ドット絵の大きさとセルの正規化（透明な縁を削る）で許容できる |
| D-03 | 常にインデックスカラー（最大 256 色） | Aseprite と同じ 3 モード。16 ビットのパレット番号 | 根幹の方針（インデックスが正本）。3 モードを持つと、検証・描画・書き出しのすべてに分岐が入り、「パレット外の色が入り込めない」保証がモードによって崩れる。256 色は `.aseprite` のインデックスモードと GIF の上限に一致する |
| D-04 | パレットはプロジェクトに 1 つ | フレームごとのパレット | パレットロックと検証を単純に保つ。色を動かす演出は別の番号で描けば表せる |
| D-05 | フレーム番号は 0 始まり（GUI の表示だけ 1 始まり） | すべて 1 始まり | `.aseprite` の形式と、シートの JSON を読む側の慣例が 0 始まり。API とデータを揃えるほうが取り違えが少ない。人間向けの表示は慣れに合わせる |
| D-06 | ID は連番。正本に時刻と乱数を入れない | UUID | 「同じ操作列から同じバイト列」を守るため。連番はエージェントにも読みやすい（`L3`） |
| D-07 | Op レジストリを唯一の変更経路にする。Op 名 = MCP ツール名 | CLI、MCP、GUI のそれぞれに実装を持つ。Op 名を `draw.line` のように階層化し、MCP 名と別にする | 3 つの利用面の挙動が食い違うのを構造的に防ぐ。名前が 1 つなら、文書もエラーメッセージも 1 種類で済む |

| D-09 | 履歴はスナップショット方式。取り消しは新しいリビジョン | 逆操作（差分）の記録。リビジョンを巻き戻す | ドット絵のプロジェクトは小さいので、全体のスナップショットで足りる。実装が単純で、Op ごとに逆操作を書く必要がない。リビジョンが常に増えれば、同時編集の照合（`expect_revision`）が単純になる |
| D-10 | セルを正規化する（透明な縁を削る、空のセルを消す） | 描いたままの矩形を保持する | 同じ絵が、操作の順序によらず同じ JSON になる。差分と冪等性の判定が正確になる。代償は、空セルが `.aseprite` との往復で失われること |
| D-11 | 決定性を 2 水準に分ける。PNG は自前ライター | 「常にバイト同一」とだけ書く。Pillow で PNG を書く | zlib の実装（従来の zlib と zlib-ng）で圧縮後のバイト列が変わりうるため、「常にバイト同一」は守れない約束になる。ピクセルの同一性を全環境で保証し、バイト同一が必要な用途には無圧縮（`stored`）を用意するのが、正直で検証可能な定義である。自前ライターにするのは、補助チャンクやフィルタの選び方をライブラリの版に左右されないようにするため |
| D-12 | 合成は整数演算。v1 のブレンドは Normal だけ | 19 種を v1 で実装する。浮動小数で計算する | 整数なら全環境で同じ結果になる。ブレンドモードは、インデックス正本では合成結果がパレット外の色になるため使用頻度が低く、v1 の必須ではない。値は保持するので往復では失われない |
| D-13 | 色距離は固定小数点 Oklab | RGB のユークリッド距離。重みつき RGB。浮動小数の CIELAB（ΔE） | RGB の距離は知覚と合わず、最近色の選び方が不自然になる。浮動小数の立方根は、数学ライブラリの実装で最下位ビットが変わりうる。整数の立方根と固定の表を使えば、どの言語でも同じ結果になる |
| D-14 | 量子化は自前の整数メディアンカットと整数 k-means。代表色は実在の色 | Pillow の量子化。scikit-learn の k-means。混合ガウス | ライブラリの版や乱数に結果が左右されない。代表色を「重心に最も近い実在の色」にすると、元画像にない濁った中間色がパレットに入らず、ドット絵らしい色面になる |
| D-15 | OpenCV、scikit-image、SciPy を依存にしない | 画像処理をライブラリに任せる | 必要な処理（差分信号、連結成分、中央値）は小さく、整数だけで書ける。PyPI の OpenCV の wheel には LGPL のバイナリが同梱されていることがあり、方針（LGPL を必須依存にしない）に触れる |
| D-16 | PixelOE は任意の extra | 必須依存。移植して同梱 | PyTorch が重く、起動時間と導入の手間が増える。v1 は任意にし、需要があれば v1.x で NumPy 実装を移植する（Apache-2.0 なので帰属表示つきで可能） |
| D-17 | `.aseprite` は `aseprite` パッケージをアダプタ越しに使う | 最初から自前で実装する | 既に公開仕様から独立に書かれた Apache-2.0 の実装があり、発注者の方針（パーミッシブな部品を積極的に使う）に合う。若いライブラリなので、隔離と代替案を用意した |
| D-18 | GUI は Web 技術とローカルサーバ | Qt（PySide）。Godot。Dear PyGui。Tkinter | Qt は LGPL。Godot は別の言語とビルド系が増える。Dear PyGui と Tkinter は、指定のテーマ（白と水色の基板風、ピクセルアート調）を作り込む表現力が足りない。Web は CSS で意匠を自由に作れ、実装モデルが最も得意で、エージェントの変更を見守る用途ではブラウザで開けるのが便利 |
| D-19 | GUI の合成はサーバ（コア）が行う | TypeScript で合成を再実装する | 合成の実装が 2 つあると、表示と書き出しが食い違う。ドット絵は小さいので、ローカルの往復で十分速い。描きかけの線だけはクライアントで仮に描くが、確定はサーバが行う |
| D-20 | MCP はステートレス。任意コード実行のツールは作らない | セッションに「現在のスプライト」を持つ。スクリプト実行ツールを出す | 現行の MCP 仕様に合う。状態の取り違えが起きない。任意コード実行は、エージェントの安全性と決定性の両方を壊す |
| D-21 | 冪等性クラスと冪等キー | 冪等性を個々の説明文に任せる | エージェントは通信の失敗で同じ呼び出しを再送することがある。クラスを明示し、冪等でない Op にはキーで再送の安全を与える |
| D-22 | 変更のたびにプレビューと差分を作る | 呼び出し元が毎回プレビューを要求する | 「見て直す」ループを既定にする。画像そのものを毎回返すとコンテキストを使うので、既定はパスだけを返し、必要なときに画像を取る |
| D-23 | Python 3.12 以上、uv、pydantic、click | Python 3.10 以上。Poetry。dataclasses と手書きの検証 | `aseprite` パッケージが 3.12 以上を要求する。pydantic は、引数の検証と JSON Schema の生成を 1 つの定義で行える |
| D-24 | Lua を載せない | Lua の実行環境を組み込む。Aseprite の Lua API 互換を目指す | 無制限の実行環境を持たない方針。API の互換は、他製品の API の文面や構造の写しに近づく危険もある |
| D-25 | 生成物は `source/` まで | 生成してそのままレイヤーに置くツール | 生成物は格子もパレットも持たない。パイプラインを通す経路だけにすれば、「キャンバスに入るのはパイプラインの出力だけ」が構造で保証される |
| D-26 | 重みは同梱しない。承諾を記録する | Apache-2.0 の重みだけ同梱する | 容量と管理の負担。ライセンスの種類によらず同じ扱いにするほうが、取り違えが起きない |

| D-28 | アイコンとフォントは自作。フォントは OFL-1.1 まで | 既存のアイコン集を使う | 他製品との類似を避け、ピクセルアート調の一貫した意匠にする。アイコンを CyberSprite 自身で作れば、道具の実地試験にもなる |

| D-30 | API に「現在の選択範囲」を持たない | サーバ側に選択範囲を持つ | 状態を持つと、エージェントと GUI が互いの選択を壊す。領域を引数にすれば、Op は単独で意味が決まる |

## 4. 第 1 弾調査（GPL 前提の旧調査）から引き継いだ注意点

第 1 弾調査は、LibreSprite（GPL-2.0）を土台にする前提だった。方針が Apache-2.0 に変わったので結論は使わないが、次の注意点は今も有効である。`docs/SPEC.md` §2 に反映した。

| 注意点 | CyberSprite での扱い |
|---|---|
| Aseprite は EULA のもとにあり、改変版を第三者に再配布できない | フォークしない。コードを読まない。公開文書と実機の画面から「事実」だけを得る |
| LibreSprite は GPL-2.0。コードを取り込むと全体が GPL になる | 取り込まない。読んで写すこともしない |
| GPL 系のツール（Krita、GIMP、Tiled のエディタ本体、ComfyUI）は、別プロセスとして横に置くことしかできない | 必須依存にしない。ユーザーが自分で入れたものとの連携は、ファイルか HTTP 越しに限る |
| Tiled は、エディタが GPL、`libtiled` と TMX 形式が BSD という分割になっている | 形式だけを使う（v1.x の書き出し） |
| pngquant / libimagequant は GPL-3.0 と商用のデュアル | 使わない。量子化は自前 |
| ニューラルなピクセル化（Make Your Own Sprites）は非商用の研究用途限定 | 使わない |
| LoRA やチェックポイントは、コードとは別のライセンスを持つ（OpenRAIL-M、CC BY-NC、独自条件）。配布元によって条件の表記が食い違うこともある | 同梱しない。アダプタとベースを別々に記録し、承諾を求める |
| FFmpeg はビルドの選択肢でライセンスが変わる | 使わない。動画の書き出しは v1 の範囲外 |
| LibreSprite 向けの MCP サーバ（GPL-2.0）は、作者自身が「壊れやすい」と書いている | エディタのスクリプト機能にぶら下がる方式は不安定。自前のコアを直接呼ぶ B 案の根拠の 1 つ |
