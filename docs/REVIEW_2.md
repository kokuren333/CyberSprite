   - 申し送り 9（ピクセル化 OSS）。接続の境界はいまのままでよい。製品の既定は変えなくてよいが、標準ワークフローの入口（生成した三面図）では内蔵の自動検出が働いておらず、入口の既定を決め直す必要がある。中立ベンチは、既定を決める根拠にならない（H-26〜H-30）。

   - **ソースの公開は、条件つきで可。** クリーンルームとライセンスに、公開を止めるような逸脱は見つからなかった。公開の前に、R2-11、R2-12、R2-01 を済ませる。

#### R2-04 描画の仕事量の見積りが粗く、通常の操作を拒否する

- **仕様の節**: §5.11
- **根拠**: 再現した［実行・本人］。1 回の Op の上限は 1,048,576（`drawing_work_per_op`）。

### 3.3 なぜ届かないのか（要因）

**要因 1: 禁じた図形の隣の図形に移っただけ。**
- R1 の分析（楕円 26 個）を受けて、手順書は「体の部品を、楕円 1 個ずつで作っていないか」と書いた。作り手はそれを守り、「楕円は使っていない」と記録した。代わりに使われたのは `polygon` で、部品 1 つが多角形 1 つである。
- 症状を名指しで禁じても、次に安い操作へ移るだけだった。**これは R1 の私の設計の読み違いである。** 直すべきは「どの図形を使うか」ではなく、「形をどこから持ってくるか」だった。

**要因 2: 設計と制作をつなぐ計測がない。**
- 関門 (1) で原画を決めても、段 3 の絵がそこからどれだけ離れたかを、道具は何も言わない。作り手は横に並べたシートを見て「原画と比べて体が大きく、頭が箱型」と気づいていた（記録 §3 の関門 (3)、疑う箇所 2）。気づいたうえで、直さずに仕上げへ進んでいる。自律タスクでは関門で止まらないので、気づきが行動に変わらない。
- 「原画の形を写す」ことは、ここでは禁じ手ではない。原画は自分たちの設計である。写す手段が、目で見比べて多角形の頂点を打ち直すことしかないのが問題である。

**要因 3: 三面図の正面を、そのまま完成形の姿勢にした。**
- 三面図（正面・側面・背面の直立）は、設計を固めるための資料である。この粒度の戦闘スプライトは、斜めを向き、重心を片側に置き、左右が非対称である（参照の人物 3 点の左右対称性は 21〜49%、道 A の胴体は 100%）。
- 手順書は、三面図から完成形の姿勢へ移る段を持たない。「向きごとにシルエットを作る」とあるので、作り手は正面図をなぞる形で組んだ。**これも上流の設計（R1 §3.4）の穴である。**

**要因 4: 影が帯になった。**
- 影は `shift_ramp` を多角形の領域にかけて作られた。頭は、上に明るい帯、下に暗い帯。脚と腕は、縦の帯。R1 の「縁に沿った三日月」は消えたが、多角形の辺に平行な帯になった。
- 形を説明する影（頭が襟に落とす影、襟が腹に落とすぎざぎざの影、付け根の暗がり）は入っている。ここは前進である。

**要因 5: 目は直った。ただし、原画より小さい。**
- 1 個 12×12（縁込み）、頭の幅に対して 0.26。層は「暗い縁 → 琥珀の輪 → 黒い瞳 → 白の点」で、×1 でも輪として読める。R1 の最大の敗因は解消した。
- 設計の指示は「頭の幅の約 3 分の 1」、参照の計測は 0.34。頭が設計より太ったぶん、比が下がっている。要因 2 と同じ根である。

**要因 6: 動きは、部品の平行移動のままである。**
- つぶれのコマ（頭の上が 1 px 下がり、頬が 1 px 張り出す）は入った。ほかは 1 px の上下とまばたきである。80×80 では 1 px の移動はほとんど見えない。

**要因 7: 関門が、自律タスクでは関門として働かない。**
- 3 枚のシートは作られ、記録も規則どおりである（自己採点なし、疑う箇所 3 つ、前後の並置、`pending`）。**報告の規律は守られた。** これは R1 からの大きな改善である。
- ただし「見せた相手: 未提示」が 3 つ並ぶ。人間が止めない限り、作り手は自分の疑いを抱えたまま最後まで進む。疑う箇所 1〜3 は、どれも関門 (2) の時点で見えていたものである。

#### 5.1.4 追加する設計

**H-26 診断と復元を分ける。** 申し送りが Fixer を推した理由は、検出の結果（列数、行数、刻み、合意度）を JSON で返し、検証ループに組み込めることだった。いまの接続は `reconstruct` の 1 段にまとまっていて、検出の値は報告の奥（stage2 の metrics）に入る。

- `import_image` と `convert` の予行（`dry_run`、`pipeline_only`）に `diagnose: true` を足す。内蔵と、導入済みで許可された外部方式のそれぞれについて、検出だけを行い、候補を並べて返す。
- 返すもの: `candidates: [{method, cols, rows, step_x_x1000, step_y_x1000, confidence, fits_platform, stage1}]`。刻みは千分率の整数で持つ（原則 3。外部方式の浮動小数は、境界で整数に丸める）。`stage1` は、その候補の格子線を元画像に重ねた画像のパス。
- **方式どうしの一致を、信頼の手がかりにする。** 列数と行数が ±1 で一致した候補が 2 つ以上あれば `agreement: true`。一致しなければ警告にし、エージェントは `stage1` を見て選ぶ。選んだ候補は `grid: {mode: "fixed", …}` として明示し、来歴に残る。
- 自動では切り替えない。同じ引数から同じ結果が出る、という性質を守るためである（導入済みの外部方式の有無で結果が変わってはならない）。

**H-27 プラットフォームから目標の寸法を取る。** e2e-07 では、Fixer の出力が 77×109 で 80×80 に入らず、捨てられた。刻みの推定が縦横で違っていた（8.16 と 7.69）。内蔵には `force_square` があるが、外部方式には掛からない。

- パイプラインの設定に `grid.fit: {max_w, max_h, square: true}` を足す。省略時、プロジェクトにプラットフォームがあり `asset.canvas.fixed` が真なら、キャンバスの大きさを使う。
- 内蔵の候補選びは、`fit` に収まる候補だけを対象にする。外部方式には、`square` のとき縦横の刻みの平均（整数に丸める）を渡して復元させる。方式がそれを受けられなければ、復元の結果が `fit` を超えた時点で不合格にし、ヒントに「`grid.mode: target` で寸法を指定する」を書く。
- 関門 `fits_canvas` は、いまは配置のはみ出しだけを見る。プラットフォームがあるとき、結果がキャンバスの面積の 4 分の 1 に満たない場合も警告にする（512×320 の写真が 8×5 として通る、という R1-06 の残り 2 件は、80×80 のプロジェクトではここで止まる）。

**H-28 原画の切り出しを、道具の中で行う。** 三面図には 3 体が入っている。e2e-07 は、正面の 1 体を道具の外（Pillow）で切り出し、別のソースとして登録し直した。

- `import_image` と `add_source` に `source_rect: {x, y, w, h}`（元画像の座標、再標本化なし）を足す。来歴に `derived_from` と矩形を記録する。
- `render_preview` の `guide` にも同じ矩形と、整数分の 1 の縮小を足す（H-23 と共通。§5.2）。

**H-29 失敗したときのヒント。** `grid_detected: false` のエラーに、次の一手を順に書く。(1) `diagnose` で候補を見る。(2) プラットフォームがあれば、`grid.mode: target` にキャンバスへ収まる寸法を入れる。(3) 外部方式が導入済みなら、その名前。未導入なら、名前と「利用者が導入する」こと。

**H-30 ベンチを作り直す。** 既定を決める材料にするなら、次を満たす。

1. **較正に使っていない原画**を使う。自作の原画を新しく起こすか、CC0 の素材を出典つきで入れる（§11.9 は CC0 を認めている）。
2. **劣化は、生成画像の崩れ方に寄せる。** 縦横で違う非整数倍、行ごとに少しずつずれる格子、色のにじみ、縁のアンチエイリアス。整数倍の最近傍は 1 系列にとどめる。
3. **系列ごとに報告する。** 全体を 1 つの率にまとめない。件数と、区間（たとえば 17 件中 13 件なら 50〜93%）を添える。
4. **各方式を、上流の既定と、アダプタの設定の両方で測る。**
5. **生成画像 (d) に、人が数えた正解を付ける。** 13 枚なら、格子線を重ねた画像を見て列数と行数を数えられる。±1 セルを一致とする。数えるのは Opus、抜き取りの確認は人間。
6. **目標寸法の部門を足す。** 全方式に同じ目標寸法を渡し、画素の一致を比べる。実際の制作の条件はこちらである。
7. **アニメーションの部門を足す。** 自作の 4〜8 コマを同じ劣化にかけ、コマ間で格子とパレットが揃うか、ちらつき（同じ場所の画素がコマ間で変わる数）を測る。

#### 5.1.5 関門の 95% について（仕様の改訂案）

R1-06 で求めた「ドット絵でない画像の 95% 以上が不合格」は、83.3%（10/12）のまま動かなかった。D2 の追加実験は、しきい値を上げると生成画像の正例が落ち、小さい格子を禁じると本物の小さい絵が落ちることを示している。**単一のしきい値でこの 2 つを分けられない、という結果を受け入れる。** §11.9 を書いた私の条件が、この指標の組では満たせないものだった。

改訂案。

1. §11.9 の条件を「(e) と (f) の 95% 以上が不合格」から、「(e) と (f) の**すべてが、不合格か警告になる**（黙って通るものが無い）。不合格の率は測って記録する」に改める。通った 2 枚（風景の写真、球）は、どちらも警告つきである。
2. 厳しさは、呼び出し側が選ぶ。`on_gate_warn: "accept" | "reject"`（既定 `accept`）を足す。人が見ない一括処理では `reject` を使う。これで (e) は 12/12 が不合格になる。正例の一部も落ちるが、それは呼び出し側が選んだ結果である。
3. 手順書の規則「警告つきで通った取り込みは、段階画像を見てから先へ進む」は、すでにある（`AGENTS.md` §6.4）。H-27 のプラットフォームとの寸法の照合が、もう 1 枚の網になる。

#### H-23 設計との一致を測る

関門 (1) で人間が決めた原画は、その後の制作の基準になる。そこからの距離は、美的な自己採点ではなく、測れる事実である。

- **`guide` の拡張。** `guide: {source, file, rect: {x, y, w, h}, fit: "canvas" | {w, h}, key: [r, g, b] | null, key_tolerance, mode: "side" | "overlay"}`。
  - `rect` は原画の中の 1 体を切り出す。`fit` は、切り出した範囲を整数の箱で平均して、指定の大きさに縮める（各出力画素 = 対応する入力画素の整数平均。割り切れない倍率は、入力の画素を出力の升に整数の規則で割り振る）。プレビューの装飾であり、正本には入らない。
  - これで、1752 px の原画を並べられない問題（制作記録 §6 の 1）も解ける。作り手が道具の外で縮小版を作って登録し直す必要がなくなる。
  - `mode: "overlay"` は、原画のシルエットの外周線を、拡大したスプライトの上に 1 色で重ねたパネルを足す。R1 の H-11 で v1.x に送った「重ねて透かす表示」の、線だけの版である。
- **計測。** `key` があるとき、レビューシートの結果と `validate` の `metrics.design` に次を入れる。水準は情報で、関門にしない。
  - `silhouette_iou_permille`（位置を ±8 px の範囲でずらした最大値と、そのずれ）
  - `area_permille`（スプライトの不透明 ÷ 原画の不透明）
  - `bbox_delta`（外接矩形の差）
  - `row_width_delta_max`（行ごとの幅の差の最大と、その行）
  - `part.` のスライスが両方にあれば、部品ごとの同じ値
- **どの原画と比べるかは、プロジェクトが覚える。** `set_design_reference`（mutate、I）で `{source, file, rect, fit, key}` を `project.json` の `design` に書く。`platform` と同じく省略可のキーである。
- 手順書には「関門 (2) と (3) で、設計との一致を照合の表に書く。外れているなら理由を書く。外れたまま残してよい」とだけ書く。姿勢を変えた場合（H-25）は、姿勢の原画と比べる。

今回の値を当てはめると、道 A は 720‰・面積 1285‰、道 B は 942‰・1006‰ になる。関門 (2) でこの数字が出ていれば、作り手の疑い（「胴が原画より太い」）は、数字つきで記録に残った。

#### H-24 道 C: 取り込みを下書きにして、打ち直す

- 段 3a で、段 2 の原画（の 1 体）を変換パイプラインで取り込み、`blocking` という名前のレイヤーに置く。これがブロッキングであり、関門 (2) のシートになる。
- 段 3b で、その上に部品のレイヤーを作る。**形は下書きから取り、色とドットは手で決める。** そのために、領域の形を 1 つ足す。
  - `{"type": "layer", "layer": <レイヤー>, "frame": <省略時は対象と同じ>, "colors": [<色>, …] | null}`: 指定したレイヤーのセルで、不透明な（`colors` があればその色の）画素の集合。
  - `mask.region` と組み合わせると、「下書きの紫の範囲にだけ、`@plum2` を塗る」「下書きのシルエットの中にだけ描く」が 1 回でできる。下書きの色は使わない。色は名前つきのランプから選ぶ。
- 仕上がったら、`blocking` を消すか、非表示にして残す。非表示のレイヤーは書き出しに入らない。
- 道 A（見て打つ）と道 B（取り込んで直す）は残す。道 C を足し、定期の e2e で 3 つを並べる。

これは「原画をなぞる」ことだが、原画は自分たちの設計であり、来歴つきでパイプラインを通っている。他人の絵をなぞらない、という §3.6 の規律とはぶつからない。参照（他人の絵）を `blocking` に入れることは、`import_image` の時点で規律違反であり、これまでどおり禁じる。

#### H-25 姿勢の原画

- 三面図は、設計を固める資料である。完成形の姿勢ではない。

1. **e2e-07 の合否。** 見比べるものは、制作記録の末尾にある（道 A、道 B、待機アニメーション、関門 (3) のシート）。私の所見は §3 だが、合否は発注者のものである。

3. **利用条件が `unknown` の生成画像を、公開リポジトリに含めるか**（R2-12）。推奨: 較正コーパスは残し、権利の状態を `NOTICE` に明記して、配布物からは外す。e2e-07 の 1752 px の原画は、縮小した見本だけを残す。

6. **§11.9 の「95% が不合格」の条件を改めること**（§5.1.5）。仕様の正本の変更である。私が書いた条件が満たせないものだった、という訂正なので、承認を求める。
