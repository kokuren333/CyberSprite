# turnaround-parts — 三面図から部品へ（大きなスプライト）

**使う場面**: 1 体のキャラクターや生き物で、1 コマがおおむね 48 px 以上のもの。DS 級の 80×80、96×96、モダンな 64〜128 px の立ち絵など。プラットフォームの `workflow` が `turnaround-parts` のとき（`docs/REVIEW_1.md` §3.1.4）。

小さなもの（32 px 以下）は [`direct.md`](direct.md)、極小で制約の厳しいもの（16×16・3 色など）は [`silhouette-first.md`](silhouette-first.md)。

## 1. 思想と原則

- **大きなキャンバスは、描きながら設計すると崩れる。** 80×80 の試作は、検証も書き出しもすべて通ったのに、発注者の評価は不合格だった（`docs/REVIEW_1.md` §2.2）。設計（原画）を先に固め、人間が見てから打つ。
- **分担**（`docs/SPEC.md` §16.2）:
  - 原案の生成（通常の三面図、ピクセルアート風の三面図）は **Codex の imagegen**。
  - 原画の解釈、ドットを打つこと、見た目の判断は **Opus**。
- **原画は見本であって、正本ではない。** ピクセルとパレットは、Opus が Op で決める。原画の色でパレットを汚さない。
- **作法の数値（§5）は物差しであって、規則ではない。** 自分の絵と照合し、外れていたら理由を考える。外れたまま残してよい。
- **人間が見る関門が 3 つある**（§2）。見た目の合格を、自分で宣言しない。判定欄は人間が決めるまで `pending` のまま（`docs/SPEC.md` §13.7）。

## 2. 段と関門

| 段 | 担当 | すること | 関門 |
|---|---|---|---|
| 0 | Opus | プラットフォームを決め、案内文を読む。参照があれば計測値を読む（[`references.md`](references.md)） | |
| 1 | Codex | 通常の三面図（正面、側面、背面）を生成する。来歴つきで登録する | **(1) 設計** |
| 2 | Codex | 1 をもとに、ピクセルアート風の三面図を生成する。粒度と色は最終形に寄せきらない。登録する | |
| 3a | Opus | 向きごとに、原画を横に並べたプレビューを見ながら、1 色でシルエットを作る。顔を先に決める（目の寸法を物差しと照合する） | **(2) ブロッキング** |
| 3b | Opus | 部品をレイヤーに分ける。色面 → 影（原画の影の「形」を拾う）→ 輪郭 → 行データで仕上げ | **(3) 仕上げ前** |
| 4 | Opus | 向きとコマをフレームとタグにまとめる。動きを付ける（[`animate`](../animate/SKILL.md)） | |
| 5 | Opus | 検証、書き出し、書き出したファイルの確認（[`validate-export`](../validate-export/SKILL.md)） | |

**3 つの関門**（`docs/SPEC.md` §13.7）:

1. **設計が決まったとき。** 原画（段 1、必要なら段 2）を見て、方向を決める。
2. **ブロッキングが済んだとき。** シルエットと顔が、×1 の実寸で読めるか。
3. **仕上げの前。** 色面・影・輪郭が入り、細部を詰める前。

- 対話できるとき: 関門ごとにレビューシートを見せ、返事を待つ。
- 対話できない自律タスク: シートを書き出して先へ進み、最終報告に 3 枚とも載せる。判定は `pending` のまま渡す。
- レビューシートの中身と作り方は [`validate-export`](../validate-export/SKILL.md) §2.5。

## 3. 手順

`csp` は `uv run --project <リポジトリ> csp`。MCP ではツール名 = Op 名。

### 3.0 準備

```text
<作業ディレクトリ>/
  hero.csprite/        正本（プロジェクト）
  design/              生成した原画と、生成の記録（送った指示、Codex のログ）
  review/              関門ごとのレビューシート（参照を含まないものだけ）
  REVIEW.md            制作記録（skills/templates/review-record.md を写したもの）
```

- プラットフォームを決める。`new --platform` と案内文（`get_info` の `include: ["platform"]`）は M11 で追加される。まだ無ければ、キャンバスの大きさ、色数の上限、陰影の段数、輪郭の扱いを `REVIEW.md` に書いておく。
- 制作記録を [`../templates/review-record.md`](../templates/review-record.md) から作る。関門のたびに埋める。

### 3.1 参照を取って測る

作風の指定や参照があるときは、参照ライブラリ（人がブラウザなどで見て保存したもの）にあるものを計測して物差しにする。足りなければ、何が要るかを利用者に頼む（エージェントは資料サイトから自分で取得しない）。置き場所、してよいこと・してはならないこと、記録の仕方は [`references.md`](references.md)。参照の画像は imagegen に渡さない（同ページ §3）。

### 3.2 Codex に原画を頼む（段 1、段 2）

**呼び出し方。** Opus の作業から、Codex を非対話で 1 回呼ぶ。指示は標準入力から渡す。

```powershell
Get-Content design/prompt-1.txt -Raw -Encoding utf8 |
  codex exec -m gpt-6.1-sol -c model_reasoning_effort=medium --dangerously-bypass-approvals-and-sandbox -C <作業ディレクトリ> - |
  Tee-Object design/codex-1.log
```

- `-C` は Codex の作業ディレクトリ。ここに原画を保存させる。
- 指示の中で「内蔵の画像生成ツールを使い、PNG を `design/turnaround-v1.png` に保存する」と明記する。
- 生成された画像は、Codex 側の `~/.codex/generated_images/` の下にも出る。指定の場所に無ければ、そこから `design/` へ**写す**（移動しない。生成の記録として残す）。
- 送った指示（`prompt-1.txt`）とログは、来歴の材料として残す。

**指示の書き方。**

- **肯定形で書く。** 「〜を描かない」は、かえって描かれることがある（発注者の申し送りの DM 知見 5。`docs/REVIEW_1.md` §3.4）。「背景は単色の〇〇」「正面・側面・背面の 3 体を横に等間隔で並べる」のように、欲しい状態を書く。
- **背景は、題材の色から遠い単色にする。** 青い背景で生成した青いキャラクターは、背景抜きで体まで抜けた。題材が青なら背景はマゼンタ、緑なら紫、のように選び、選んだ色を記録する。
- 3 体の高さとアイラインをそろえる、と書く。後で向きどうしを照合しやすい。
- 参照から測った数値を使うなら、数値として書く（例「頭の幅に対する目の幅を 3 分の 1 ほどにする」「1 素材の陰影は 3 段」）。参照の画像も、既存の作品名やキャラクター名も渡さない。

**段 1（通常の三面図）の指示の例。**

```text
内蔵の画像生成ツールで、オリジナルのキャラクターの三面図（デザインシート）を 1 枚作り、
PNG で design/turnaround-v1.png に保存してください。
- 題材: 苔の生えた石の背中を持つ、小型の四足の生き物。丸い大きな目。
- 正面・側面・背面の 3 体を、同じ縮尺、同じ地面の高さで、横に等間隔に並べる。
- 背景は単色のマゼンタ（#ff00ff）。
- 線ははっきり、色面は平らに、影は 1 段。
保存したファイルのパスを最後に 1 行で書いてください。
```

**段 2（ピクセルアート風の三面図）の指示の例。** 段 1 の画像を作業ディレクトリに置き、指示の中でファイル名を指す。

```text
design/turnaround-v1.png の三面図をもとに、ピクセルアート風の三面図を 1 枚作り、
design/turnaround-pixel-v1.png に保存してください。
- 3 体の配置、縮尺、背景のマゼンタ（#ff00ff）はそのまま。
- 1 体の高さが、およそ 80 ドットに見える粗さ。
- 素材ごとに 3 段の陰影、輪郭は素材のいちばん暗い色。
保存したファイルのパスを最後に 1 行で書いてください。
```

- 段 2 は、最終の粒度への橋渡しである。最終の制約（正確な大きさ、色数）に寄せきらなくてよい。寄せきるのは段 3 の仕事。
- 案を比べたいときは、指示を変えて 2〜3 枚作り、関門 (1) で並べて見せる。順位は付けない（`validate-export` §2.6）。

**登録する。** 原画はキャンバスに入れずに、来歴つきで残す。

- `add_source`（M12 で追加）: 画像を `source/` に登録し、来歴に `use: "design"` を記録する。`provenance` は `kind: "generated"`、`provider: "codex-imagegen"`、`model: "gpt-6.1-sol"`（ツールが明示した値だけ）、`prompt`（実際に送った指示）、`license: "unknown"`、`rights_note`（`docs/GENERATION.md` と台帳 L-12）。
- `add_source` がまだ無いとき: `design/` に画像と指示とログを置いたままにし、`REVIEW.md` に来歴の項目を書く。`add_source` が入ったら登録する。**原画を見るためにキャンバスへ `import_image` しない**（原画の色がパレットに入る）。
- 原画を並べて見るプレビュー `render_preview` の `guide`（M12 で追加）: `{"source":"SRC1","mode":"side","scale":4}` のように指定すると、原画が同じ倍率で横に並ぶ。原画はプレビューの装飾で、正本にもパレットにも入らない。まだ無ければ、プレビューの PNG と原画を並べて開く。

### 3.3 関門 (1) 設計

- 見せるもの: 段 1 の三面図（案が複数なら順位なしで並べる）、段 2 があればそれも。決めたいこと（頭身、色調、目の形）を 1〜3 行。
- 決まったら、制作記録の関門 (1) に、選ばれた案、日付、コメントを書く。

### 3.4 段 3a ブロッキング（シルエットと顔）

道は 2 つある。**どちらが良いかは、まだ分かっていない。** 定期の e2e では両方を試し、発注者が見て決める（`e2e-tests/README.md`）。

**道 A: 原画を見ながら手で打つ。**

1. プラットフォームの大きさで `new` し、パレットを先に決める（素材ごとのランプ。§5）。
2. 向きごとにフレームかレイヤーを分け、**1 色で**シルエットを打つ。`polygon` や `draw_rows` で輪郭線を取り、内側を `fill`。楕円 1 個を体の部品 1 個にしない（§5）。
3. **顔を先に決める。** 目の位置、大きさ、層（輪郭 → 明るい輪 → 瞳）を、ほかの部品より先に置く。
4. 原画を横に並べたプレビュー（§3.2）で、向きごとの比率を見比べる。

**道 B: ピクセルアート風の三面図を取り込んで、手で直す。**

1. 段 2 の画像を変換パイプラインで取り込む（[`import-convert`](../import-convert/SKILL.md)）。まず `convert` で試し、段階画像を見る。背景は段 2 で指定した色を `background.mode: "key"` で抜く。
2. パイプラインの段の方式を、入力に合わせて選ぶ。今回の修正で次の 3 つが選べるようになる（M12 で追加。方式の正確な名前と引数は `docs/SPEC.md` §11 と `csp ops describe import_image`）:
   - 格子の復元・精密（Pixel Art Fixer）: 格子のあるドット絵風の画像。
   - アニメーション向け（proper-pixel-art）: 複数のコマで、格子とパレットを共通にしたいとき。
   - 写真・イラスト向け（PixelOE）: 格子のない絵（段 1 の三面図を直接変換する場合など）。
3. 取り込んだら、向きごとに切り分け、シルエットと顔を手で直す。取り込んだ結果は「下書き」であり、そのまま仕上げにしない。

どちらの道でも、ブロッキングが済んだら関門 (2) のシートを出す。

### 3.5 関門 (2) ブロッキング

- 見せるもの: レビューシート（×1 の実寸、整数倍、シルエット、原画との並置）。
- 問うこと: ×1 でシルエットが読めるか。顔（とくに目）が読めるか。向きが見分けられるか。
- 自分で疑っている箇所を 3 つ、座標つきで制作記録に書いてから見せる。

### 3.6 段 3b 部品、色面、影、輪郭、仕上げ

1. **部品をレイヤーに分ける**（頭、胴、手前の脚、奥の脚、目など）。重なりの前後がレイヤーの順になる。
2. **色面**: 部品ごとに素材の中間色で塗る。
3. **影**: 原画の影の「形」を拾う。光源を 1 つ決め、頭が胴に落とす影、脚の付け根の暗がり、重なりの奥を先に置く。縁に沿った三日月から始めない（§5）。
4. **輪郭**: 外周の一部を最も暗い色、残りを素材の最も暗い色にする（色つきの選択的な輪郭）。`outline` は使ってよいが、結果を見て手で直す。
5. **仕上げ**: 行データ（`draw_rows`、`skip_transparent`）で 1 px 単位に詰める。目、口、爪、ハイライト。
6. 1 つの意図ごとに 1 トランザクション。毎回、検証デルタとプレビューを見る（[`draw-sprite`](../draw-sprite/SKILL.md)）。

### 3.7 関門 (3) 仕上げ前

- 見せるもの: レビューシート一式（明るさだけの版を含む）。前の関門のシートとの前後比較と、前の版のリビジョン番号。
- 疑っている箇所 3 つを更新して書く。

### 3.8 段 4・段 5

- 動き: [`animate`](../animate/SKILL.md)。大きなスプライトでは、平行移動だけでは動いて見えにくい。部品ごとに形を変えるコマを作り、少ないユニークなコマを並べ替える作り方がある（§5）。
- 検証と書き出し: [`validate-export`](../validate-export/SKILL.md)。最終報告は同 §2.6 の規則で書く。

## 4. 生成画像の扱い（まとめ）

- キャンバスに入る経路は `import_image` だけ（道 B）。
- 見本としての原画は `source/` に `use: "design"` で残す（`add_source`、M12 で追加）。
- どちらも来歴（提供元、モデル、実際の指示、ライセンス `unknown`、権利のメモ）を空にしない。

## 5. 測った観察（80×80 級。照合用で、規則ではない）

DS 世代の市販スプライト 4 点（人物 3、生き物 1）を測った値と、不合格だった試作との比較（`docs/REVIEW_1.md` §2.2、`docs/reference/PROVENANCE_LOG.md`）。点数が少ない。合否の基準にはしない。自分の絵と照合し、外れていたら理由を考える材料にする。

| 観点 | 参照で測ったもの | 不合格だった試作 |
|---|---|---|
| 目の大きさ | 頭の幅の約 0.34 | 0.20（手前）、0.12（奥） |
| 目の構造 | 暗い輪郭 → 明るい輪（2 px）→ 黒い瞳、の 3 層。最も暗い色と最も明るい色が隣り合う | 黒い円盤に白 2〜3 px。×1 では黒い点 2 つ |
| 影 | 頭が胴に落とす影、付け根の暗がりなど、形を説明する影 | 縁に沿った三日月とハイライトの楕円（球の塗り方） |
| 体の作り | 部品ごとに輪郭が違う | 楕円の和集合。関節も重なりの理屈もない |
| 陰影の段数 | 素材ごとに 3 段。肌と白は 2 段 | — |
| 輪郭 | 外周の 40〜64% が最も暗い色、残りは素材の最も暗い色 | — |
| ディザ | ほとんど無い | — |
| 色数（透明を除く） | 人物 14〜15、生き物 11 | 13 |
| 占有（不透明 ÷ キャンバス） | 人物 16〜17%、生き物 24% | 51% |
| 輪郭からの最大の深さ | 人物 10〜11 px、生き物 17 px | 27 px |
| 動き | 7 枚ほどのユニークなコマの並べ替え ＋ 上下動 | 平行移動とまばたきだけ |

- 小さい絵では 1 px がそのまま意味の単位になる（目は 2 px）。80 px では、目や手は**設計する部品**になる。
- 色数や迷子ピクセルのような衛生の指標では、この差は測れなかった。差は設計の構造（目、遠近、影の意味）にある。
- 部品の比は、名前が `part.` で始まるスライスを付けると測れるようになる（`craft.parts`、M13 で追加）。それまでは `pixels --rect` で数える。

## 6. 失敗チェックリスト

- [ ] 原画なしで、描きながら設計していないか。
- [ ] 関門のシートを出さずに、次の段へ進んでいないか。
- [ ] 見た目の合格を自分で宣言していないか。判定は `pending` のままか。
- [ ] 原画を見るために、キャンバスへ取り込んでいないか（パレットが汚れる）。
- [ ] 体の部品を、楕円 1 個ずつで作っていないか。
- [ ] 目を、ほかの部品の後回しにしていないか。×1 で輪として読めるか。
- [ ] 影が縁に沿った三日月だけになっていないか。形を説明する影があるか。
- [ ] Codex への指示を否定形で書いていないか。背景の色は題材から遠いか。
- [ ] 参照の画像、既存の作品名やキャラクター名を imagegen に渡していないか。
- [ ] 生成画像の来歴（実際の指示、ライセンス `unknown`）を残したか。`~/.codex/generated_images/` から写したか。
- [ ] 「改善」のたびに、前後のシートと前の版のリビジョン番号を残したか。
